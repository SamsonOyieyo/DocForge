# Engine packaging and OTA updates

DocForge treats every engine as an independent, versioned package. The app
ships small seed packages, extracts them into private storage, resolves
executables through one manager, and can replace a single engine without an app
release. The design is modelled on YTDLnis — with one important correction
about what Android actually allows.

- Runtime: `lib/core/engines/engine_manager.dart` (+ installer, store, manifest)
- CI: `.github/workflows/engines.yml`, `tool/engines/*.py`
- Registry: `engines/engines.json`
- Release tag: `engines` (rolling)
- Manifest URL:
  `https://github.com/SamsonOyieyo/DocForge/releases/download/engines/engines_manifest.json`

> **Windows today:** the shipped installer bundles QPDF directly through
> `tool/bundle_qpdf.ps1`, and `assets/engines/seeds.json` is empty. The OTA
> registry below is the path for additional engines and for updating QPDF
> without a new app build; see [`ENGINES.md`](ENGINES.md) section 9.

---

## 1. The Android reality (read this first)

The premise "extract the binary into app storage and exec it" no longer holds
for store builds:

- Android 10 (API 29) removed the `execute` permission on files in the app's
  home directory for apps targeting API 29+. `Process.start` /
  `Runtime.exec` on a downloaded binary in `getFilesDir()` fails with `EACCES`,
  even if the file is `chmod 755` and owned by the app.
- APK assets are not executable at all: `assets/` is not a real filesystem
  path that the kernel can exec.
- The only app-owned, exec-allowed location is `ApplicationInfo.nativeLibraryDir`
  (`/data/app/.../lib/<abi>`), which the package manager populates from
  `jniLibs` — read-only, and only refreshed by an APK update.

This is exactly how YTDLnis works: its **fixed runtimes** (Python, FFmpeg) ship
as `libpython.so` / `libffmpeg.so` in `jniLibs`, while the part that updates
OTA is `yt-dlp` — a **Python script**, executed by the bundled interpreter.
Scripts and data do not need the execute bit, so they can live in app storage
and be hot-swapped freely.

DocForge therefore distinguishes **runtime** from **payload**:

| Package `runtimes` | Where it lives | Hot-swappable on Android |
| --- | --- | --- |
| `process` (native CLI) | Extracted executable | **No** (API 29+). Desktop: yes. |
| `script` (Python/shell run by a fixed interpreter) | App storage | **Yes** |
| `data` (tessdata, presets, dictionaries) | App storage | **Yes** |
| `ffi` (native `.so`) | APK `jniLibs` | No (`.so` load is exec-gated too) |

`EngineManager` enforces this: on Android it lists `process` packages but marks
them **not installable** with an explanation. Two supported ways forward:

1. **Play Store / modern targetSdk**: ship QPDF/Tesseract as APK-native FFI
   libraries and use OTA only for scripts and `tessdata`. The `EngineTool` API
   does not change when a CLI engine is later replaced by an FFI build.
2. **Self-hosted / F-Droid**: an app targeting API 28 still has execute
   permission on its data directory, so full binary OTA works there. Set
   `allowAndroidProcessEngines = true` in `EngineManager` **only** for such
   builds (Play requires targetSdk 35+ as of 2025).

Desktop (Windows, macOS, Linux) has no such restriction; the full OTA path
works today, which is why desktop is the first adoption target.

## 2. Manifest

`engines_manifest.json` is generated by CI, attached to the rolling `engines`
release, and fetched by the app. Assets are per platform:

```json
{
  "schema": 1,
  "generatedAt": "2026-10-21T12:00:00Z",
  "engines": {
    "qpdf": {
      "version": "12.4.2",
      "releasedAt": "2026-10-21T12:00:00Z",
      "license": "Apache-2.0",
      "runtimes": ["process"],
      "notes": "Faster linearisation.",
      "assets": {
        "windows-x64": {
          "version": "12.4.2",
          "url": "https://github.com/SamsonOyieyo/DocForge/releases/download/engines/qpdf-12.4.2-windows-x64.zip",
          "sha256": "9f2c…64 hex chars…",
          "size": 8421376
        },
        "linux-x64": { "version": "12.4.2", "url": "…", "sha256": "…", "size": 14680064 }
      }
    }
  }
}
```

Rules:

- **Platform keys** are `<os>-<arch>`: `android-arm64-v8a`,
  `android-armeabi-v7a`, `android-x86_64`, `android-x86`, `windows-x64`,
  `windows-ia32`, `windows-arm64`, `macos-x64`, `macos-arm64`, `linux-x64`,
  `linux-arm64`. The mapping lives in `engine_platform.dart`.
- **`asset.version` is authoritative for that platform.** `release.version` is
  the newest version across assets. This lets a single-ABI rebuild ship without
  marking other ABIs as outdated.
- **Versions are monotonic.** A package on the release tag is never mutated —
  versioned filenames stay downloadable, which also gives rollback history.
  Only the manifest is re-uploaded (`--clobber`).
- **`schema`** is checked; a newer manifest is rejected with an actionable
  error instead of being guessed at.
- **Unknown engines are ignored** by the UI; unknown fields are ignored by the
  parser, so the manifest can grow without breaking old clients.

`EngineManager` caches the last good manifest in `<engines>/manifest.json`, so
the update list survives offline launches; a failed check never clears it.

## 3. On-disk layout and hot-swap

```
<application support>/engines/
  state.json                     {"engines": {"qpdf": {"active": "12.4.2",
                                 "previous": "12.3.0", "origin": "ota", …}}}
  manifest.json                  last fetched manifest (offline cache)
  qpdf/
    12.3.0/                      previous, kept for instant rollback
    12.4.2/                      active
      engine.json                id, version, executables, license, runtimes
      bin/qpdf
      lib/libqpdf.so.30          LD_LIBRARY_PATH is exported per job
  .tmp/                          staging + `.trash-*` (wiped every launch)
  .downloads/                    partial downloads (wiped every launch)
```

Install sequence (`engine_installer.dart`):

1. Stream the download to `.downloads/`, checking its size (when the manifest
   publishes one) and its SHA-256 against the manifest.
2. Extract into `.tmp/<engine>-<version>-<stamp>/`; the archive library skips
   entries that would escape the target directory, and a package that ends up
   without a valid `engine.json` is rejected.
3. Validate `engine.json`: id must match the requested engine, version must
   match the requested version, declared executables must exist.
4. `chmod 755` declared executables on POSIX (zip mode bits are preserved too).
5. Move the existing target version to `.trash-*` (never mutate a directory a
   running process may be using), rename staging into
   `<engine>/<version>/`, then write `state.json` **last**.
6. Prune to `active` + `previous`; failures are retried on the next launch.

Consequences:

- A crash or failed checksum leaves the old version active and runnable.
- `previous` is a one-click rollback (`EngineManager.rollback`), useful when a
  new engine release regresses a conversion.
- Two versions can be installed at once, so an in-flight job keeps the path it
  started with.
- Windows cannot delete a running `.exe`; the delete is deferred by design.

Seeds (`assets/engines/seeds.json` + `<engine>-<platform>.zip`) use the same
installer. Seeding happens only when nothing is installed or the bundled seed
is newer than the active version, so a fresh APK never downgrades an OTA
engine. Seeding failures are warnings, never startup blockers.

## 4. Runtime integration

`EngineManager` is Flutter-free and testable in plain Dart:

| Member | Purpose |
| --- | --- |
| `initialize()` | load state, reconcile disk, extract seeds, read manifest cache |
| `checkForUpdates()` | fetch manifest, return newer packages for this platform |
| `applyUpdate(update)` | download → verify → extract → hot-swap → prune |
| `rollback(tool)` | swap `active` and `previous` |
| `managedPaths` | engine id → executable path |
| `searchDirectories` | package roots for `Toolkit.detect` |
| `environment` | merged `LD_LIBRARY_PATH` / `DYLD_LIBRARY_PATH` / `PATH` |
| `pendingUpdates`, `installing`, `downloadProgress`, `lastError` | UI state |

Wiring in the app:

```dart
// AppState.initialize()
final manager = EngineManager(
  root: Directory(p.join(support.path, 'engines')),
  manifestUrl: Uri.parse(settings.engineManifestUrl ?? defaultEngineManifestUrl),
  loadSeedAsset: _loadSeedAsset,           // rootBundle → Uint8List
);
await manager.initialize();
_engineManager = manager;

// Toolkit: explicit override > managed package > bundled folder > PATH
_toolkit = await Toolkit.detect(
  overrides: settings.toolPaths,
  managedPaths: manager.managedPaths,
  searchDirectories: engineDirectories,
);
```

The job layer is untouched: `toolPaths` is still the only contract, so existing
jobs and tests keep working. Bundled shared libraries are the one new piece:

```dart
// tool_page.dart
JobRunner.start(request.copyWith(
  toolEnvironment: app.engineManager?.environment ?? const {},
));
```

`JobRequest.toolEnvironment` is plain data and is applied by
`process_runner.setEngineEnvironment` inside the job isolate. Windows resolves
DLLs from the executable directory, so this mainly matters on Linux/Android
(`LD_LIBRARY_PATH`) and macOS (`DYLD_LIBRARY_PATH`).

Network posture: `autoUpdateEngines` defaults to **false**, and DocForge still
never uploads a document. A check downloads only the manifest (a few KB,
metadata); the Settings toggle enables a launch-time check. `autoUpdateEngines`
plus `engineManifestUrl` are stored in the existing settings JSON
(backward-compatible). `DOCFORGE_ENGINE_MANIFEST_URL` can be baked at build
time for staging or self-hosted mirrors.

## 5. CI pipeline

```
engines/engines.json ──► matrix.py ──► jobs per (engine × target)
      engines/<id>/build.sh <target> <outdir>       compile or stage
      tool/engines/package.py                       zip + SHA-256 + meta.json
              │
              ▼ artifacts
tool/engines/manifest.py merge ──► engines_manifest.json ──► gh release upload
```

Run it from **Actions → Engine packages → Run workflow** (optionally narrow
`engines`, `targets`, or override `version`), or push a tag matching
`engine-v*`.

`engines/engines.json` is the single source of truth:

```json
{
  "engines": {
    "qpdf": {
      "version": "12.4.2",
      "license": "Apache-2.0",
      "runtimes": ["process"],
      "targets": ["windows-x64", "linux-x64"]
    }
  }
}
```

The build contract for `engines/<id>/build.sh` is small:

```bash
#!/usr/bin/env bash
set -euo pipefail
target="$1"; out="$2"          # e.g. windows-x64, android-arm64-v8a
mkdir -p "$out/bin"
cp /path/to/<id> "$out/bin/"    # plus lib/, share/, NOTICE as needed
```

`package.py` then:

- writes/updates `engine.json` at the archive root,
- zips deterministically (sorted entries, pinned timestamps, 0755 for `bin/*`),
- prints the SHA-256 and writes `<engine>-<version>-<target>.meta.json`.

`manifest.py merge` folds new metadata into the **previous** manifest fetched
from the release, so rebuilding one engine preserves every other engine.
`manifest.py seeds` hashes downloaded zips into `assets/engines/seeds.json` for
app builds that want bundled baseline engines.

The workflow is generic: add an engine by writing its `build.sh` and adding one
registry entry. `engines/scaffold/` is a runnable end-to-end smoke test;
`engines/qpdf/build.sh` shows the packaging half for a portable QPDF build
(cross-compiling Android is intentionally not attempted — see §1).

Operational notes:

- `concurrency: engine-packages` serialises manifest merges; without it two
  runs can overwrite each other's engine entries.
- Only the publish job has `contents: write`.
- Old versioned zips are kept on the rolling release, so the app can still
  download the version it was pointed at, and rollback assets stay available.
- To serve a different manifest, point `engineManifestUrl` at it or rebuild
  with `--dart-define=DOCFORGE_ENGINE_MANIFEST_URL=…`.

## 6. Adopting this without breaking the current app

The layer was added *around* the existing detection flow, not in place of it.
Refactor order that keeps every workflow green:

1. **Detection stays authoritative (already done).** `Toolkit.detect` resolves
   in order: explicit setting → managed package → bundled `engines/` folder →
   `PATH` → known install locations. A user override still wins, so nobody's
   custom QPDF path is silently replaced.
2. **Seeds are additive.** With an empty `seeds.json` the manager is a no-op;
   system installs, `tool/stage_engines.ps1`, and existing tests behave exactly
   as before. Android ships no seeds initially.
3. **Jobs keep `toolPaths`.** Managed engines only change *where* the path
   points. `JobRequest.toolEnvironment` defaults to `{}`, so old callers and
   tests are unaffected.
4. **UI is opt-in.** Settings gains an "Engine updates" section; auto-check is
   off by default. Every failure (offline, malformed manifest, blocked package
   on Android) surfaces a message and leaves the current engine installed.
5. **Desktop first.** Windows/macOS/Linux can execute downloaded binaries, so
   ship OTA there while Android uses APK-native engines.
6. **Android later, via FFI or scripts.** Replace `Process`-based engines with
   FFI bindings (`libqpdf`, `libtesseract`, PDFium) shipped in `jniLibs`; keep
   `EngineTool`/`Toolkit` as the abstraction so job code does not change. Run
   Python/shell engines as scripts through a fixed interpreter in
   `nativeLibraryDir`, YTDLnis-style; those payloads remain hot-swappable.
7. **Sign releases before broad rollout.** TLS + SHA-256 protects against
   corruption and a compromised CDN, but not a compromised repository. Add
   minisign/cosign over the manifest and pin the public key in the app when the
   distribution grows.

## 7. Testing

`test/engine_manager_test.dart` covers the parts that must never regress:
platform key mapping, manifest parsing/schema rejection, version ordering,
disk reconciliation, pruning, seed extraction, checksum rejection, hot-swap
with rollback, and the Android `process`-package guard. Everything runs against
temp directories and injected fakes — no network.

Manual smoke test on desktop:

```powershell
# 1. Publish an engine package (Actions → Engine packages)
# 2. Launch DocForge, Settings → Engine updates → check for engine updates
# 3. Apply; verify the card reports the new version and a job still runs
# 4. Roll back (code path: EngineManager.rollback) if the engine regresses
```

## 8. Release checklist

- [ ] Bump the engine version in `engines/engines.json` (never reuse a version).
- [ ] Run the Engine packages workflow; confirm the summary table.
- [ ] Verify `engines_manifest.json` on the `engines` release has the new
      `version` per asset.
- [ ] Desktop smoke test: seed on fresh profile, update, run a real job.
- [ ] Android: confirm the package is marked not installable unless it is
      `script`/`data` (or the build intentionally targets API 28).
- [ ] Keep the previous version asset on the release so rollback works.
